详细贡献操作指南
前提
确保你的电脑已经安装 Git（安装教程：[Git 官方安装指南](https://git-scm.com/book/zh/v2/%E8%B5%B7%E6%AD%A5-%E5%AE%89%E8%A3%85-Git)），并已登录 GitHub 账号。

#步骤 1：Fork 仓库（把仓库复制到自己账号下）
这一步的目的是：在不影响原仓库的前提下，在自己的账号下创建仓库副本，所有修改都在副本上进行。
1. 打开你的仓库页面（比如 `https://github.com/yuyiren777/王道数据结构25版大题代码`）；
2. 找到页面右上角的 `Fork` 按钮（紫色/灰色按钮，很显眼），点击它；
3. 等待几秒，GitHub 会自动在你的账号下创建一个和原仓库完全一样的副本；
4. 跳转后，页面地址会变成 `https://github.com/贡献者账号/王道数据结构25版大题代码`，说明 Fork 成功。

> ❗ 新手注意：Fork 只需要做一次，后续修改不需要重复 Fork。

步骤 2：克隆 Fork 后的仓库到本地
这一步的目的是：把线上的仓库副本下载到自己的电脑里，方便修改代码。
1. 打开你 Fork 后的仓库页面，找到绿色的 `Code` 按钮，点击后复制 `HTTPS` 地址（比如 `https://github.com/贡献者账号/王道数据结构25版大题代码.git`）；
2. 打开电脑的终端/命令行（Windows 用 CMD/PowerShell，Mac/Linux 用 Terminal）；
3. 输入以下命令（把地址换成你复制的自己的仓库地址）：
   ```bash
   # 克隆仓库到本地，会在当前目录创建一个和仓库同名的文件夹
   git clone https://github.com/贡献者账号/王道数据结构25版大题代码.git
   
   # 进入克隆后的文件夹（必须进入，否则后续命令会报错）
   cd 王道数据结构25版大题代码
   ```
4. 执行完后，查看你的电脑文件夹，会出现仓库的所有文件，说明克隆成功。

> ❗ 新手注意：
> - 克隆地址一定要用自己 Fork 后的地址，不是原仓库地址；
> - 如果克隆时提示“权限不足”，检查是否登录了正确的 GitHub 账号，或换成 SSH 地址（新手优先用 HTTPS）。

### 步骤 3：创建新分支（避免直接修改主分支）
这一步的目的是：**隔离修改内容，防止直接改主分支导致代码混乱，也方便后续审核**。
1. 确保终端已经进入仓库文件夹（步骤 2 的 `cd` 命令已执行）；
2. 先查看当前分支（确保在主分支，通常是 `main` 或 `master`）：
   ```bash
   git branch
   ```
   输出里带 `*` 的就是当前分支，比如 `* main`。
3. 创建并切换到新分支（分支名要清晰，格式：`类型-模块-问题`）：
   ```bash
   # 示例1：修复第3章数组越界问题
   git checkout -b fix-ch3-array-outofbound
   
   # 示例2：优化第5章链表注释
   git checkout -b optimize-ch5-linklist-comment
   
   # 示例3：新增第4章栈的题解
   git checkout -b add-ch4-stack-solution
   ```
4. 再次执行 `git branch`，会看到 `* fix-ch3-array-outofbound`，说明分支创建并切换成功。

> ❗ 新手注意：
> - 分支名不要用中文、空格或特殊符号；
> - 一个分支只改一个问题（比如只修复一个瑕疵），不要一个分支改一堆内容，方便审核。

### 步骤 4：修改代码（聚焦问题，保持整洁）
这一步的核心是：**只改有瑕疵的部分，不要动无关代码，保持代码风格和原项目一致**。
1. 用你熟悉的编辑器（VS Code/CLion 等）打开本地仓库文件夹；
2. 找到要修改的文件（比如 `第3章/3.2 数组题.c`），只修改有瑕疵的代码：
   - 比如原代码有数组越界：`for (int i = 0; i <= n; i++)` → 改成 `for (int i = 0; i < n; i++)`；
   - 改完后保存文件，确保代码能正常运行（编译/执行无报错）。

> ❗ 新手注意：
> - 不要随意修改原代码的变量名、注释风格、缩进方式；
> - 改完后一定要自己先测试，确保修改后的代码能正常运行，没有引入新问题。

### 步骤 5：提交修改（清晰备注，方便追溯）
这一步的目的是：**把本地的修改记录下来，备注要明确说明“改了什么、为什么改”**。
1. 先查看修改的文件（确认只改了要改的文件）：
   ```bash
   git status
   ```
   红色的就是修改过的文件，确认无误后继续。
2. 将修改的文件加入暂存区：
   ```bash
   # 推荐：只添加要修改的文件（精准）
   git add 第3章/3.2 数组题.c
   
   # 快捷方式：添加所有修改的文件（如果只改了一个文件，可用）
   git add .
   ```
3. 提交修改（备注信息要清晰，格式：`[类型] 模块：具体修改内容`）：
   ```bash
   # 示例1：修复问题
   git commit -m "[修复] 第3章3.2题：修复数组越界问题"
   
   # 示例2：优化内容
   git commit -m "[优化] 第5章5.1题：完善链表注释，补充逻辑说明"
   
   # 示例3：新增内容
   git commit -m "[新增] 第4章4.3题：添加栈的顺序存储实现代码"
   ```
4. 执行完后会输出类似 `1 file changed, 1 insertion(+), 1 deletion(-)`，说明提交成功。

> ❗ 新手注意：
> - 提交备注不要写“修改代码”“修复bug”这种模糊的话，必须说明“改了哪个文件、什么问题”；
> - 如果一次改不完，可以多次提交，但最终推送到远程前，尽量合并成一个清晰的提交（新手可忽略）。

### 步骤 6：推送到自己的 Fork 仓库
这一步的目的是：**把本地分支的修改上传到你 GitHub 账号下的 Fork 仓库里**。
1. 确保终端还在仓库文件夹，且在新建的分支下；
2. 执行推送命令（分支名要和本地一致）：
   ```bash
   # 推送 fix-ch3-array-outofbound 分支到自己的 Fork 仓库
   git push origin fix-ch3-array-outofbound
   ```
3. 首次推送可能需要输入 GitHub 账号和密码（或个人访问令牌），按提示输入即可；
4. 执行完后，打开你 Fork 后的仓库页面，会看到新分支 `fix-ch3-array-outofbound`，说明推送成功。

> ❗ 新手注意：
> - 如果推送失败，提示“权限不足”，检查是否登录了自己的 GitHub 账号；
> - 如果提示“分支不存在”，确认分支名拼写正确。

### 步骤 7：发起 Pull Request (PR)（请求合并修改到原仓库）
这一步是核心：**向原仓库发起请求，让仓库主人（你）审核并合并你的修改**。
1. 打开你 Fork 后的仓库页面，会看到一个黄色的提示条：`Compare & pull request`（对比并发起 PR），点击它；
2. 进入 PR 编辑页面，重点填写 3 部分内容：
   - **标题**：和提交备注一致即可，比如 `[修复] 第3章3.2题：修复数组越界问题`；
   - **描述框**：简单说明：
     - 原问题是什么（比如“第3章3.2题的循环条件错误，导致数组越界”）；
     - 你改了什么（比如“将循环条件 i <= n 改为 i < n”）；
     - （可选）测试结果（比如“修改后编译运行，输出结果正确，无越界报错”）；
   - **目标分支**：确认“base repository”是原仓库（你的账号），“base”是 `main`/`master`；“head repository”是你的 Fork 仓库，“compare”是你新建的分支（`fix-ch3-array-outofbound`）；
3. 确认无误后，点击绿色的 `Create pull request` 按钮，发起 PR；
4. 发起成功后，你（仓库主人）会收到 GitHub 的通知，PR 会出现在原仓库的 `Pull requests` 标签页里。

> ❗ 新手注意：
> - PR 发起后，不要删除自己的分支，也不要再往这个分支推送新内容（除非仓库主人要求修改）；
> - 如果 PR 描述不清楚，仓库主人可能会在评论区问你，及时回复即可。

---

### 额外补充：PR 发起后可能的情况
1. **审核通过，合并成功**：（仓库主人）会把你的修改合并到主分支，此时你可以删除自己的分支（可选）；
2. **需要修改后再审核**：仓库主人会在 PR 评论区指出问题（比如“这里改得不对，应该xxx”），你需要：
   - 回到本地的该分支，继续修改代码；
   - 再次执行 `git add .` → `git commit -m "补充修改：xxx"` → `git push origin 分支名`；
   - 推送后，PR 会自动更新，不需要重新发起；
3. **PR 被关闭（不合并）**：仓库主人会说明原因（比如“这个修改不符合项目规范”），不用灰心，这是开源协作的正常情况。

---

总结核心逻辑：**Fork（复制）→ 分支（隔离）→ 修改（聚焦）→ 提交（清晰）→ 推送（上传）→ PR（请求合并）**，全程不直接修改原仓库；
